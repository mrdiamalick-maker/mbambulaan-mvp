# Mbàmbulaan — Roadmap MVP

## 1. Objet du document

Ce document transforme l'architecture métier de Mbàmbulaan en plan d'exécution.

Le MVP n'a pas pour objectif de digitaliser toute la filière, ni de démontrer le plus grand nombre de fonctionnalités. Il doit prouver une boucle de coordination complète, mesurable et suffisamment utile pour justifier :

- l'adoption terrain ;
- un financement institutionnel ou privé ;
- une première volonté de payer ;
- une réplication sur d'autres sites ;
- la poursuite de l'investissement produit.

---

## 2. Thèse du MVP

Le premier MVP doit démontrer qu'en anticipant un retour, en rendant visibles les besoins et capacités, puis en suivant les engagements jusqu'au résultat, Mbàmbulaan peut réduire une perte opérationnelle concrète et produire une preuve économique de cette valeur.

### Boucle de référence

```text
Retour annoncé
→ Besoin de service déclaré
→ Capacité disponible recherchée
→ Tension créée si insuffisance
→ Responsable mobilisé
→ Engagement suivi
→ Arrivée et débarquement confirmés
→ Pesée et lot enregistrés
→ Résultat mesuré
→ Valeur ou perte évitée documentée
```

Le MVP doit exécuter cette boucle de bout en bout sur un territoire réel.

---

## 3. Problème prioritaire à tester

Le problème initial proposé est :

> Les retours et volumes sont insuffisamment anticipés, tandis que les capacités critiques de glace, froid, transport et manutention sont mal visibles ou mobilisées trop tard, ce qui provoque attente, congestion, dégradation de qualité et perte de valeur.

Ce problème est retenu car il :

- est transversal à plusieurs acteurs ;
- crée une perte économique observable ;
- permet une intervention avant la vente ;
- ne nécessite pas de remplacer les pratiques commerciales existantes ;
- mobilise le coeur différenciant de Mbàmbulaan : visibilité, allocation et coordination.

---

## 4. Cas d'usage principal

### Coordination d'un retour avec besoin critique de service

Un capitaine ou relais annonce un retour avec heure estimée, volume et besoin de glace, froid ou transport.

Le gestionnaire ou coordinateur identifie une capacité disponible. Si la capacité est insuffisante, une tension est créée, un responsable est désigné et un engagement est suivi.

À l'arrivée, le débarquement et la pesée sont confirmés. Le service rendu et le résultat sont enregistrés. La valeur créée ou la perte évitée est estimée.

### Pourquoi commencer par les services

- la ressource est identifiable ;
- le fournisseur est identifiable ;
- le bénéficiaire est identifiable ;
- l'exécution peut être prouvée ;
- la valeur économique est plus simple à mesurer ;
- le risque de devenir une marketplace est réduit.

---

## 5. Périmètre territorial

Le MVP doit être concentré sur :

- un seul territoire pilote ;
- un site de débarquement principal ;
- éventuellement un second site uniquement comme solution de réorientation ;
- un nombre limité d'acteurs engagés ;
- une ou deux capacités de service prioritaires.

Le choix du territoire doit être fondé sur :

- l'existence d'un problème fréquent et coûteux ;
- la présence d'un sponsor local ;
- l'accès réel aux acteurs ;
- la possibilité de collecter les données ;
- la présence d'au moins un opérateur de service ;
- une gouvernance locale praticable ;
- une activité suffisante pour produire des cas pendant le pilote.

Le territoire définitif ne doit pas être inscrit dans le code avant validation terrain.

---

## 6. Acteurs requis pour le pilote

### Noyau opérationnel minimum

- 1 gestionnaire de site ou responsable opérationnel ;
- 1 coordinateur local ou agent de site ;
- 3 à 10 capitaines, propriétaires ou relais à terre ;
- 1 fournisseur de glace ou opérateur de froid ;
- 1 transporteur ou solution logistique mobilisable ;
- 1 organisation de pêcheurs ou structure de représentation ;
- 1 sponsor institutionnel ou territorial.

### Acteurs facultatifs en phase initiale

- acheteur professionnel ;
- transformateur ;
- agent de contrôle ;
- second opérateur de capacité ;
- programme ou bailleur.

### Principe

Le pilote ne doit pas dépendre d'une mobilisation massive. Il doit fonctionner avec une coalition réduite mais réellement active.

---

## 7. Capacités incluses dans le MVP

### Socle acteur et confiance

- enregistrer acteurs, organisations et rôles ;
- rattacher les acteurs à un territoire et à un site ;
- distinguer déclaration, confirmation et vérification ;
- conserver l'auteur et l'horodatage d'une action.

### Visibilité opérationnelle

- annoncer un retour attendu ;
- mettre à jour l'heure estimée d'arrivée ;
- déclarer une estimation simple de volume ;
- déclarer un besoin de service ;
- confirmer une arrivée.

### Traçabilité minimale

- confirmer un débarquement ;
- enregistrer une pesée ;
- qualifier la méthode ou le niveau de confiance ;
- constituer un ou plusieurs lots ;
- contrôler la cohérence entre poids pesé et lots.

### Capacité et allocation

- déclarer une capacité de glace, froid ou transport ;
- visualiser sa disponibilité ;
- proposer une correspondance simple ;
- réserver ou affecter une capacité ;
- confirmer l'exécution du service.

### Coordination

- signaler et qualifier une tension ;
- rattacher la tension à un retour, un lot ou un service ;
- désigner un responsable ;
- formaliser un engagement et une échéance ;
- suivre le statut ;
- clôturer avec preuve.

### Mesure de la valeur

- enregistrer un résultat ;
- mesurer le délai de résolution ;
- estimer la quantité protégée ou sauvée ;
- estimer une valeur en FCFA ;
- documenter la méthode de calcul et son niveau de confiance.

### Adoption terrain

- permettre la saisie assistée ;
- fournir une vue opérationnelle simple ;
- envoyer des notifications essentielles, lorsque le canal est disponible.

---

## 8. Capacités explicitement exclues

Le MVP ne doit pas inclure :

- paiement intégré ;
- portefeuille numérique ;
- crédit ou financement ;
- assurance ;
- scoring avancé ;
- automatisation algorithmique du matching ;
- place de marché publique complète ;
- enchères ;
- comptabilité ;
- gestion de stock interne exhaustive ;
- traçabilité réglementaire nationale exhaustive ;
- couverture nationale ;
- intégrations lourdes ;
- application distincte pour chaque catégorie d'acteur ;
- reporting institutionnel complexe non issu des opérations.

Ces exclusions protègent le MVP contre la dispersion et la surconstruction.

---

## 9. Hypothèses à tester

### H1 — Utilité opérationnelle

Les acteurs considèrent l'anticipation des retours et la coordination des services comme suffisamment utiles pour changer une partie de leurs pratiques.

### H2 — Qualité de la donnée

Les informations minimales peuvent être produites assez tôt et avec un niveau de fiabilité suffisant pour déclencher une action.

### H3 — Coordination

La formalisation d'un responsable, d'un engagement et d'une échéance améliore réellement le taux ou le délai de résolution.

### H4 — Valeur économique

Le pilote permet d'éviter ou de réduire une perte mesurable en kilogrammes, temps ou FCFA.

### H5 — Volonté de payer privée

Un gestionnaire, opérateur de capacité ou acheteur accepte de payer pour une capacité directement liée à un gain.

### H6 — Volonté de payer institutionnelle

Une institution accepte de financer le déploiement, le pilotage ou la coordination territoriale.

### H7 — Coût d'exploitation

Le service peut être opéré avec un coût compatible avec les revenus futurs.

---

## 10. Indicateurs de succès

### Adoption

- nombre d'acteurs effectivement actifs ;
- part des retours pilotes annoncés avant l'arrivée ;
- fréquence de mise à jour ;
- proportion d'opérations saisies sans intervention directe de l'équipe centrale ;
- taux de réutilisation hebdomadaire.

### Opérations

- nombre de retours coordonnés ;
- nombre de besoins de service déclarés ;
- nombre de capacités disponibles ;
- nombre de réservations ou allocations ;
- taux d'exécution des engagements ;
- délai moyen de résolution des tensions.

### Qualité et confiance

- proportion de retours confirmés ;
- proportion de pesées enregistrées ;
- cohérence entre poids et lots ;
- part des actions avec auteur et preuve ;
- nombre de contestations.

### Valeur

- kilogrammes concernés par les coordinations ;
- kilogrammes estimés protégés ou sauvés ;
- temps d'attente évité ;
- capacité inutilisée mobilisée ;
- valeur estimée en FCFA ;
- coût du service de coordination.

### Économie de Mbàmbulaan

- coût de déploiement par site ;
- coût opérationnel mensuel ;
- coût moyen par retour coordonné ;
- revenu ou engagement financier obtenu ;
- volonté de renouvellement ;
- délai de paiement institutionnel ;
- marge potentielle par offre.

---

## 11. Seuils de validation initiaux

Les seuils doivent être adaptés après diagnostic terrain. Une première base de décision peut être :

### Adoption minimale

- au moins 5 acteurs opérationnels récurrents ;
- au moins 50 % des retours ciblés annoncés avant arrivée ;
- au moins 4 semaines d'usage réel.

### Exécution minimale

- au moins 20 retours coordonnés ;
- au moins 10 besoins de service enregistrés ;
- au moins 5 tensions suivies jusqu'à clôture ;
- au moins 70 % des engagements exécutés ou explicitement requalifiés.

### Valeur minimale

- au moins 3 cas documentés de perte évitée ou de service accéléré ;
- une valeur totale estimée supérieure au coût variable direct de coordination ;
- une méthode de calcul compréhensible et contestable.

### Validation économique

- au moins un payeur potentiel accepte un test tarifaire ;
- au moins une proposition écrite de poursuite, financement ou abonnement ;
- coût de support compatible avec une réplication sur plusieurs sites.

Ces seuils ne constituent pas des promesses commerciales. Ils servent de garde-fous de décision.

## 12. Phases de la roadmap

## Phase 0 — Cadrage terrain

### Objectif

Vérifier que le problème, les acteurs et le territoire correspondent aux hypothèses.

### Travaux

- sélectionner le territoire ;
- cartographier les acteurs réels ;
- observer plusieurs retours ;
- documenter les pratiques de glace, froid et transport ;
- mesurer les pertes et délais actuels ;
- identifier le décideur et le payeur ;
- obtenir un accord de pilote.

### Livrables

- diagnostic terrain ;
- coalition pilote ;
- processus actuel ;
- baseline des indicateurs ;
- protocole de données ;
- accord de collaboration.

### Décision

**Go** si le problème est fréquent, mesurable et soutenu par un sponsor local.

---

## Phase 1 — Pilote concierge

### Objectif

Tester la boucle sans dépendre d'un produit complet.

### Mode opératoire

- saisie assistée par un coordinateur ;
- outils simples ;
- notifications manuelles ou semi-automatiques ;
- traitement humain du matching ;
- collecte structurée des preuves et résultats.

### Pourquoi

Le pilote concierge permet de vérifier la valeur avant d'automatiser des comportements incertains.

### Livrables

- playbook opérationnel ;
- journal des retours ;
- journal des tensions ;
- résultats et pertes évitées ;
- retours utilisateurs ;
- premières hypothèses tarifaires.

### Décision

**Go produit** si la boucle crée de la valeur et se répète.

---

## Phase 2 — MVP numérique ciblé

### Objectif

Numériser les points de coordination répétitifs et réduire le coût du service opéré.

### Produit

- vue retours attendus ;
- annonce et mise à jour ;
- besoins de service ;
- capacités disponibles ;
- tensions et engagements ;
- arrivée, pesée et lots ;
- résultats ;
- vue opérationnelle et indicateurs essentiels.

### Livrables

- application MVP ;
- rôles et permissions ;
- données de référence ;
- support ;
- formation ;
- instrumentation des indicateurs.

### Décision

**Go réplication** si l'usage augmente et si le coût unitaire baisse.

---

## Phase 3 — Réplication locale

### Objectif

Démontrer que le modèle fonctionne sur plusieurs sites avec un coeur commun.

### Travaux

- déployer sur 2 à 5 sites ;
- standardiser les rôles et playbooks ;
- tester plusieurs opérateurs ;
- tester les abonnements et frais de réservation ;
- consolider la vue territoriale ;
- mesurer les coûts de déploiement.

### Décision

**Go réseau** si l'offre peut être répliquée sans forte personnalisation.

---

## Phase 4 — Réseau multi-sites

### Objectif

Créer des effets de réseau et une offre institutionnelle structurée.

### Travaux

- coordination inter-sites ;
- réorientation de retours ou capacités ;
- acheteurs et transformateurs multi-territoires ;
- contrats territoriaux ou nationaux ;
- intégrations partenaires ciblées ;
- produits de données agrégées.

### Décision

**Go infrastructure sectorielle** si l'usage, les revenus et la gouvernance sont durables.

---

## 13. Backlog par résultat métier

Le backlog ne doit pas être organisé par pages mais par résultats.

### Résultat A — Retour anticipé

- créer un retour attendu ;
- mettre à jour l'ETA ;
- qualifier volumes et besoins ;
- notifier le site concerné.

### Résultat B — Capacité mobilisée

- déclarer une capacité ;
- rechercher une capacité compatible ;
- affecter ou réserver ;
- confirmer l'exécution.

### Résultat C — Tension résolue

- créer et qualifier ;
- désigner un responsable ;
- créer un engagement ;
- suivre ;
- escalader ;
- clôturer avec preuve.

### Résultat D — Produit tracé

- confirmer arrivée et débarquement ;
- enregistrer une pesée ;
- créer des lots ;
- vérifier la cohérence matière.

### Résultat E — Valeur prouvée

- enregistrer un résultat ;
- calculer délai et quantité ;
- estimer valeur en FCFA ;
- présenter la preuve au payeur.

## 14. Cartographie avec le domaine existant

Le domaine actuellement implémenté couvre déjà une partie importante du MVP :

- `ExpectedReturn` → retour annoncé ;
- `Landing` → arrivée et débarquement ;
- `Weighing` → mesure de référence ;
- `Lot` → unité d'allocation ;
- `Capacity` → capacité de service ;
- `Tension` → problème coordonné ;
- `Commitment` → action et responsabilité ;
- `Outcome` → résultat et valeur.

Les services existants suivants sont alignés avec la boucle :

- `announceExpectedReturn` ;
- `confirmLanding` ;
- `registerWeighing` ;
- `createLot` ;
- `reportTension` ;
- `createCommitment` ;
- `recordOutcome`.

### Écarts à analyser avant reprise du développement

- déclaration détaillée de besoins de service ;
- gestion opérationnelle des capacités ;
- proposition et réservation de capacité ;
- désignation explicite d'un responsable ;
- suivi des échéances et escalade ;
- preuve d'exécution du service ;
- mesure structurée de la valeur en FCFA ;
- saisie assistée et permissions terrain.

## 15. Principes de développement

### Principe 1 — Une fonctionnalité doit tester une hypothèse

Aucun développement important sans hypothèse, acteur et indicateur associés.

### Principe 2 — Préserver le service humain

Ne pas automatiser trop tôt les décisions qui nécessitent encore une compréhension terrain.

### Principe 3 — Mobile et simplicité opérationnelle

Les parcours doivent être courts, adaptés à la connectivité et utilisables par un relais.

### Principe 4 — La preuve avant le dashboard

Chaque indicateur doit provenir d'un événement métier et soutenir une décision.

### Principe 5 — Un coeur commun

Éviter les versions spécifiques par site. Les différences doivent être configurables ou opérées.

### Principe 6 — La valeur doit être visible

Chaque boucle terminée doit pouvoir expliquer qui a bénéficié, quelle perte a été évitée et pourquoi Mbàmbulaan a été utile.

---

## 16. Gouvernance du pilote

### Comité opérationnel hebdomadaire

- coordinateur Mbàmbulaan ;
- gestionnaire de site ;
- représentant des pêcheurs ;
- opérateur de capacité ;
- sponsor local si nécessaire.

Objectif : examiner retours, tensions, engagements, résultats et frictions.

### Revue mensuelle de valeur

- usages ;
- résultats ;
- coûts ;
- valeur créée ;
- décisions produit ;
- hypothèses économiques ;
- risques d'adoption.

### Règle

Le pilote doit produire des décisions, pas seulement des comptes rendus.

---

## 17. Critères de Go / Pivot / Stop

### Go

- usage récurrent ;
- données suffisamment fiables ;
- valeur économique démontrée ;
- acteur local prêt à continuer ;
- payeur potentiel identifié ;
- coût de déploiement maîtrisable.

### Pivot

- problème réel mais mauvais acteur, mauvais canal ou mauvaise capacité prioritaire ;
- usage dépendant d'un intermédiaire particulier ;
- valeur créée mais modèle de paiement inadéquat ;
- difficulté de saisie nécessitant plus de service opéré.

### Stop

- problème peu fréquent ou non prioritaire ;
- absence durable de sponsor ;
- incapacité à obtenir une donnée exploitable ;
- valeur créée inférieure au coût d'opération ;
- dépendance à une personnalisation non réplicable ;
- absence de volonté de payer ou de financer la poursuite.

---

## 18. Priorités immédiates

Avant toute nouvelle vague majeure de code :

1. sélectionner le territoire et le cas de service exact ;
2. conduire le diagnostic terrain ;
3. valider la coalition pilote ;
4. définir les indicateurs de baseline ;
5. exécuter une première boucle concierge ;
6. auditer le domaine existant face aux capacités MVP ;
7. définir le backlog produit par résultat métier ;
8. seulement ensuite reprendre le développement.

---

## 19. Décision stratégique

Le MVP de Mbàmbulaan ne sera pas jugé sur le nombre d'écrans créés.

Il sera jugé sur sa capacité à démontrer qu'une coordination plus précoce, plus claire et plus traçable :

- réduit une perte ;
- améliore une décision ;
- mobilise une capacité ;
- responsabilise les acteurs ;
- crée une valeur mesurable ;
- peut être financée durablement.

Cette preuve constitue la base du produit, du modèle économique, de la légitimité institutionnelle et de l'avantage concurrentiel de Mbàmbulaan.
